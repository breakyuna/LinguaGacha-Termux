# Termux Web 改造操作标准

本文指导开发 Agent 执行本次改造，配合 [完整方案](TERMUX_WEB_PLAN.md)、[HANDOFF](../HANDOFF.md) 和 [AGENTS](../AGENTS.md) 使用。通用验证入口仍为 [WORKFLOW](WORKFLOW.md)。产品 Agent 不消费本文。

## 1. 文档职责与执行范围

|材料|维护内容|更新时机|
|---|---|---|
|`TERMUX_WEB_PLAN.md`|目标、范围、任务依赖与验收|目标或实现方案发生实质变化|
|`HANDOFF.md`|唯一任务状态、证据、阻塞与下一步|开始任务、阶段结算、暂停或交付|
|本文|改造的实施、验证与交接方法|操作方法或环境约束变化|
|`AGENTS.md`|仓库行动规则与三文档入口|开发规则或入口变化|
|现有长期工程文档|已落地且代码不能直接表达的设计意图|对应实现发生变化|

先满足用户当前任务及已有授权，再执行仓库规则。本次文档建立不启动产品改造。后续授权实施后，按任务依赖继续执行必要的本地修改和验证，不为每个子任务增加确认环节。

新增外部发布、付费调用、破坏用户数据或实质扩大产品范围时，遵循 `AGENTS.md` 的授权边界。遇到普通工具链问题，先独立排查并记录实际错误。

## 2. 每轮工作的固定步骤

1. 读取三份文档，查看 `git status --short`，核对已完成结果是否仍适用于当前代码。
2. 在 `HANDOFF.md` 选择依赖已满足的任务 ID，记录本轮目标、当前状态和影响范围。
3. 用 `rg --files` 与 `rg` 定位真实生产者、消费者和测试；先确认状态所有者、唯一写入口、取消与补偿边界。
4. 在已授权范围实现完整行为；共享契约变化同步调整调用者，避免留下假成功或半迁移入口。
5. 按变更触发验证，保存必要结果。验证失败先判断环境、测试设施或产品行为，修复后仅重跑受影响范围。
6. 审查本任务差异、命名、注释、数据边界、产品说明和文档引用。
7. 更新 `HANDOFF.md` 的任务状态、验证记录和下一步；范围或操作方法变化同步更新对应文档。
8. 交付时说明实际完成内容、验证层级及剩余影响。只在用户要求提交时创建提交，遵循仓库 Conventional Commits 约定。

只读检查任务不更新产品代码；已有无关改动不回滚、不格式化、不顺手清理。中断交接必须指出未完成的代码和残留进程，避免下一轮误用半成品。

## 3. 环境与依赖操作

### 3.1 开始实施时的检查

以下命令当前可用，均用于读取状态：

```sh
pwd
git status --short
git rev-parse --short HEAD
node --version
npm --version
node -p 'JSON.stringify({platform:process.platform,arch:process.arch,sqlite:process.versions.sqlite})'
command -v chromium-headless
command -v html-screenshot
```

- 根目录以当前工作区为准，不将本机绝对路径写进产品配置。
- 检查磁盘和内存余量后安排安装、构建和 PDF 验证，不按 CPU 数量无限创建任务或浏览器进程。
- 基础能力探针使用内存数据库或临时数据；不能用用户工程验证迁移和异常终止。

### 3.2 安装与构建边界

- `TW-01` 先核对根 `postinstall`、Electron 安装触发、平台可选依赖和锁文件，再确定 Web 安装流程。
- 不直接套用当前桌面 `npm ci` / `npm run dev` 来证明 Termux 支持。现有 `postinstall` 安装 Electron，`dev` 与 `build` 仍属于桌面路径。
- 不将全局 `--ignore-scripts` 当作最终部署方案；隔离实验若使用跳过脚本，须列出跳过内容并验证运行依赖完整性。
- 保留可复现依赖解析。确需改版本或锁文件时说明原因和影响，不删除锁文件试运气，不永久手改 `node_modules` 代替源头修复。
- Android 原生绑定须在目标环境加载验证。电脑预构建的 JavaScript 不代表其中的原生依赖也能运行；检查部署目录的实际包和 WASM。
- Android 类型检查按 [WORKFLOW](WORKFLOW.md#termux-web-运行) 准备本机编译器；核对安装版本、源码配方与缓存身份，并实际检查根配置的全部引用项目。首次源码编译需要 Go，不将开发工具部署进 Web 运行目录。
- 日常运行产物与开发工具分开验证。外部构建是工具链备选，不把上传代码、远程 CI 执行或发布作为自动授权行为。

### 3.3 命令登记

下表描述命令责任。当前命令入口见 `package.json`，用户用法见 [README](../README.md)，开发配置见 [WORKFLOW](WORKFLOW.md#termux-web-运行)，验证结果只在 `HANDOFF.md` 登记。

|目标命令|预期责任|归属任务|
|---|---|---|
|`npm run dev:web`|构建并启动 Web 服务（无开发服务器与代理，同 `build:web` + `start:web`）|`TW-02`、`TW-04`|
|`npm run build:web`|构建 Node 入口、React 页面、worker 与运行资源|`TW-02`、`TW-11`|
|`npm run start:web`|从构建产物启动本机服务|`TW-02`、`TW-11`|

类型检查、lint 和测试优先复用已有入口；确需平台区分时明确覆盖集合，不为获得绿灯静默排除受影响代码。脚本命名可随真实实现调整，但须同步三文档和使用说明。

## 4. 实现检查标准

|变更边界|实施时必须核对|
|---|---|
|组合根与服务|只有一个生命周期拥有者；资源路径显式注入；失败清理；信号处理；重复启动与停止|
|线程与子进程|部署入口可定位；取消传播；等待实际释放；父进程结束后不遗留写入者|
|任务与连接|上传/预览取消和后台任务取消分离；受理回包丢失可查询；重试不重复副作用|
|工程与数据库|复用写入口、互斥、事务与修订；提交后同步失败不重复提交；副本一致性|
|上传与目录|材料所有者和清理时机；体积与数量限制；文件名、相对路径、真实路径与允许根|
|下载与导出|访问会话、文件身份和归属校验；流式交付；多文件结构；取消不删除已提交事实|
|浏览器访问|同源、访问会话、`Origin` / `Host`、跨站防护；SSE/下载也受保护；日志脱敏|
|代理与模型|明确的代理选择；回环直连；认证回调、流式结果、失败和重试行为|
|宿主能力|前后端及产品 Agent 对能力可用性一致；不可用有明确反馈；禁止空实现假成功|
|手机交互|主要操作可触达；替代悬停/右键；软键盘、安全区、视口、滚动与草稿恢复|
|部署与更新|安装目录与数据目录分离；锁定依赖；升级前收尾；备份与数据迁移后的回滚边界|

新增结构要对应真实责任。优先提取现有组合根和文件能力，不建立泛化插件系统或无需求的双平台兼容层。测试不得读取或断言动态内置技能的具体名称、数量、顺序、元数据或内容。

## 5. 验证选择与证据

### 5.1 按变更选择验证

|改动类型|验证要求|
|---|---|
|仅三文档或 `AGENTS.md`|相对链接、任务 ID、状态一致性、入口走查、`git diff --check`|
|TypeScript、类型或解析配置|按 `WORKFLOW.md` 运行类型检查及受影响行为测试|
|源码、脚本或架构检查规则|按触发条件运行 lint、架构检查及显式路径格式检查|
|后端组合根与生命周期|目标测试加真实 Node 入口启动、关闭和失败清理|
|HTTP / SSE / 鉴权|真实监听服务测试合法会话、拒绝路径、流取消和重连|
|文件、数据库与迁移|临时目录及真实 SQLite；成功、失败、取消和旧工程副本|
|Agent 工作区|真实受限 Node 子进程、部署依赖、权限拒绝、IPC 和进程退出|
|前端交互|相关 renderer 行为测试加浏览器操作；移动系统行为另用 Android 浏览器|
|图片与 PDF|真实宿主输出、取消与进程释放；查看图片及 PDF 渲染页|
|构建、安装或发布配置|构建目标产物，仓库外启动；检查资源与目标平台绑定；全链路冒烟|

已存在的验证命令：

```sh
npm run typecheck
npm run lint
npm run check
npm run format -- --check <本任务支持格式化的文件路径...>
npm test -- --project node <目标测试文件路径...>
npm test -- --project renderer <目标测试文件路径...>
git diff --check
```

带尖括号的命令是参数模板，执行前必须替换。Markdown 不在当前项目格式化脚本处理范围内。仅文档修改不触发完整产品构建。

当前 `node` 测试项目也包含 Electron 相关测试，`renderer` 包含 preload 测试；测试项目名称不是平台兼容证明。迁移真实入口测试时保留相应生命周期覆盖，为 Web 路径建立等价验证，不批量跳过失败用例。

`WORKFLOW.md` 当前部分平台验证要求真实 Electron。实现新增 Web 构建/运行责任时，同批更新验证入口，区分 Web 与仍受影响的桌面责任；不要只修改说明取消尚需覆盖的共享行为。

### 5.2 模型与样例

- 优先使用已有 [模型模拟服务](../buildtools/mock_llm_api_server.py)，先读取其参数和支持协议；Agent 特定协议不足时补测试自有响应或专用夹具。
- 样例覆盖有效响应、慢响应、流中断、请求失败、取消和重试。记录实际覆盖的模型协议，模拟服务不证明真实模型质量。
- 使用合成文本、测试自有技能和工程副本。真实 API 费用、真实凭据、用户原稿与外部服务写入遵循已有授权。
- 新增或整理自动化测试时读取并遵循 [project-test](../.codex/skills/project-test/SKILL.md)。断言可观察行为，不断言实现文本以代替行为。

### 5.3 浏览器与 Android 验证

优先使用已配置的本机工具，以下是命令模板：

```sh
html-screenshot http://127.0.0.1:<实际端口>/ <绝对产物目录>/mobile.png 390 844
html-screenshot http://127.0.0.1:<实际端口>/ <绝对产物目录>/desktop.png 1280 900
```

需要访问会话、交互或异步加载时，用 Playwright Core，按真实页面状态等待。首次实现认证后，应通过正式会话建立流程进入页面，不能为截图关闭认证。

```js
process.env.PLAYWRIGHT_BROWSERS_PATH = '0';
const { chromium } = require('/data/data/com.termux/files/home/.local/share/html-visual-check/node_modules/playwright-core');
const { launchOptions } = require('/data/data/com.termux/files/home/.local/share/html-visual-check/browser-config.cjs');

async function verifyPage() {
  const browser = await chromium.launch(launchOptions);
  try {
    const page = await browser.newPage({ viewport: { width: 390, height: 844 } });
    // 从本次验证配置读取 URL，完成访问会话建立，等待业务状态后操作和截图。
  } finally {
    await browser.close();
  }
}
```

- 这是本机验证脚本骨架，不是产品运行依赖；产品宿主须自行配置可执行文件和浏览器生命周期。
- 截图后实际查看图片。DOM、API 成功和场景统计不能代替视觉验收。
- 视口验证包括竖屏、横屏和桌面；本机软件渲染不代表手机 GPU 性能。
- Android 真机另验证软键盘、系统文件选择器、下载、切后台、锁屏和页面恢复。自动化截图通过不能登记为这些系统行为已通过。
- 运行页面使用受信任本地内容及独立浏览器配置。当前本机浏览器使用 `--no-sandbox`，不得复用个人会话；产品图片/PDF 宿主的资源隔离须单独验收。

### 5.4 结果记录格式

在 `HANDOFF.md` 为验证分配 `V-xxx`，至少记录：日期、关联任务、代码基线、命令或方法、环境、结果和适用边界。较大的日志/截图放在临时产物目录，文档只记录路径和必要摘要，不提交凭据或用户材料。

结果使用“通过”“失败”“未运行”。环境缺失导致失败时写明原因；不能将“未运行”改写成“无需验证”。本机基础探针通过不能替代完整项目测试，模块元数据不能替代真实加载。

## 6. 进度与交接标准

任务表状态只使用以下值：

|状态|含义|
|---|---|
|待开始|尚未进入实现|
|进行中|已开始且有明确下一步|
|待验证|实现已完成，但验收证据不足|
|受阻|具体条件阻止后续推进，已记录原因与解除方式|
|完成|该任务验收条件全部满足，附验证记录|

- 总表仅在 `HANDOFF.md` 维护；方案不复制完成勾选，操作标准不维护当前进度。
- 部分完成保留为“进行中”或“待验证”，在任务详情列出已完成和剩余子项。
- 阻塞记录要包含真实错误、已排查方向、影响任务、可独立推进内容和解除条件；不得仅写“环境问题”。
- 下一步写成可执行的小目标，包含入口与首个验收，避免只写“继续优化”。
- 每轮结束核对表格、任务详情、验证记录和下一步一致，不保留过期的“正在执行”描述。
- 任务完成以对应验收证据为准。文档整理和基础探针不能替代依赖、业务或平台验收。

## 7. 更新与故障恢复验收

使用测试自有数据执行以下场景，结果归入 `TW-11`：

1. 干净目录安装核心产物，校验无 Electron 依赖的启动与核心闭环。
2. 安装可选宿主组件，验证能力信息更新及图片/PDF 输出。
3. 正常停止服务，确认任务和写入收尾，再升级程序文件；确认用户配置、工程和工作区保留。
4. 模拟启动失败或进程异常结束，重开工程并核对已提交结果与中断状态。
5. 从一致性备份恢复到独立数据目录，比较工程资产、译文、配置和必要会话事实。
6. 在明确数据格式兼容条件下验证程序回退；若迁移不可逆，使用升级前备份恢复，不直接用旧版写新数据。
7. 执行方案规定的长任务场景，登记设备、Android/浏览器版本、时长、进程和资源情况及未覆盖条件。

终端会话管理、后台运行辅助工具和电池设置只能作为操作说明，不能替代任务持久化或保证进程永久存活。
